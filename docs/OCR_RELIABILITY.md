# OCR Reliability — Runbook, num_ctx posture and measured baselines

> Phase 205 deliverable (OCR-01/02 + OCR-05 feed). The reliability verdict
> contract: **the stock `num_ctx 4096` posture silently truncates the OCR
> prompt itself at prompt-composition time** (Ollama's `chatPrompt()` drops
> content until the tokenized prompt fits `num_ctx` — image tokens count).
> This document holds the operator runbook for the fix
> (`glm-ocr-optimized`), the effective-`num_ctx` explanation, the salvage
> accounting rules, and the measured pre/post-fix metric tables.

## 1. Purpose

- Make the local vision OCR pipeline (Ollama `glm-ocr`) reliable enough that
  dense pages transcribe **completely**: no silent prompt truncation, no
  unobserved context clamps, deterministic sampling.
- Every claim in the tables below is **measured**, not assumed: pre-fix
  rows were collected by `scripts/ocr-baseline.cjs` against the
  production-default posture; post-fix rows (205-04) compare the same
  fixtures after preprocessing + prompt + num_ctx changes.

The regression suite (OCR-05) lives at
`packages/server/src/__tests__/ocrReliability.integration.test.ts` —
OLLAMA_BASE_URL-gated, Postgres-free (`jest.config.integration-nodb.js`),
4 committed deterministic fixtures (straight / rotated ~5° / table /
small-text, generated by `scripts/generate-ocr-regression-fixtures.cjs`,
each < 100KB). Run commands are in the suite's RUNBOOK header; in CI
without a daemon the suite skips with an explicit reason (never a fake
fail, never a silent skip).

## 2. Modelfile runbook — `glm-ocr-optimized` (OCR-01 / D-06)

The canonical artifact is `docker/ollama/glm-ocr-optimized.Modelfile`
(`FROM glm-ocr:latest` + exactly 4 PARAMETERs: `num_ctx 16384`,
`num_predict 8192`, `temperature 0`, `top_k 1`). The TEMPLATE block is
**intentionally absent** — the base model's bare `{{ .Prompt }}` template is
load-bearing (done-less-stream guard, see the comment block in
`packages/server/src/ocr/modelRegistry.ts`; the salvage rule 260829-lkq in
`ollamaVisionClient.ts` is the safety net, not the fix).

### Path A — node script (recommended)

```bash
# prerequisite: glm-ocr pulled on the target daemon
ollama pull glm-ocr:latest

OLLAMA_BASE_URL=http://localhost:11434 node scripts/build-glm-ocr-optimized.cjs
# → "[build-glm-ocr-optimized] created glm-ocr-optimized from glm-ocr:latest — status: success"
```

Non-throwing: success exits 0, failure logs `[build-glm-ocr-optimized] failed: …`
and exits 1 (hints included).

### Path B — docker exec (no node required)

```bash
# pipe the Modelfile through stdin (works from the host, no volume mount):
docker exec -i <ollama-container> ollama create glm-ocr-optimized -f - \
  < docker/ollama/glm-ocr-optimized.Modelfile

# or mount the repo and reference the file path inside the container:
docker exec <ollama-container> \
  ollama create glm-ocr-optimized -f /mounted/path/glm-ocr-optimized.Modelfile
```

### Verify

```bash
curl -s http://localhost:11434/api/show -d '{"model":"glm-ocr-optimized"}' \
  | jq '.parameters'   # → num_ctx 16384 / num_predict 8192 / temperature 0 / top_k 1
```

`ollama rm glm-ocr-optimized` reverts the artifact (registry entry stays
harmless — the model name simply 404s like any other unpulled model).

## 3. Effective num_ctx — request vs override vs trained cap (OCR-02, D-08/D-09)

The `num_ctx` actually sent on every OCR request resolves, in order:

1. **Env override** — `OCR_NUM_CTX` (default `0`): any value `>= 1` wins.
2. **Registry request** — `modelConfig.contextWindow` when `OCR_NUM_CTX=0`
   (`glm-ocr:*` → 4096, `glm-ocr-optimized:*` → 16384).

The **trained GGUF cap** (`<arch>.context_length`, read via
`client.show({ model }).model_info` at request time) is audited per request:

- `requested > trained` → greppable warn
  `[ocr] num_ctx requested exceeds GGUF context_length — silent clamp expected`
  with `{ model, requested, trained, effective }` structured fields.
- otherwise → info log `[ocr] effective num_ctx { model, requested, trained }`.
- `show()` failure (model not created yet → 404, daemon restart, …) → warn
  `could not read model_info … using requested num_ctx` and the OCR call
  proceeds with the requested value (fail-open; the audit never fails OCR).

Notes: the cap scan matches the `.context_length` **suffix** (the prefix is
the GGUF architecture name — glm-ocr is *not* `llama`; it is scanned, never
hardcoded). For glm-ocr the trained cap is 131072 (128K), so `num_ctx 16384`
is fully achievable — the clamp warn is belt-and-suspenders for future
models/instances. The key is set via `OLLAMA_BASE_URL` env (server) or plain
`node scripts/ocr-baseline.cjs` runs.

## 4. Salvage accounting (260829-lkq)

Every OCR run in the tables is classified into exactly one of three classes:

| Class | Meaning | How it happens |
|-------|---------|----------------|
| **clean** | stream ended with `done:true`, `done_reason:"stop"` (or `truncated` falsy) | normal |
| **salvaged** | stream ended WITHOUT the done marker but complete content had already accumulated; `truncated=true` | 260829-lkq — glm-ocr's custom engine intermittently closes the NDJSON stream after full output; the transcription is REAL and must not be discarded. **Degraded success, not a failure.** |
| **failed** | empty content + done-less stream, timeout, model absent, etc. | real failure |

Counting salvaged runs as failures overstates the failure rate; counting
them as clean hides truncation. The tables carry all three.

**Reading the post-fix numbers** (same environment as the baseline; re-run
the gated suite to refresh rows — they are machine-written, never hand-edited):

- **The degenerate fence loop is gone.** The pre-fix baseline's identical
  `4069 tokens / 5432 chars of ```-fence repetition / truncated` profile
  does not appear in any post-fix run. Every fixture now transcribes REAL
  page content — the known-content strings are found in BOTH arms on every
  fixture (`known-content=2/2`), and transcription quality is byte-stable
  pre↔post (token similarity 1.000 across the board). The 205-02
  standardized prompt + top_k 1 options posture (active in both arms via
  `ocrPage`) removed the loop; preprocessing then adds no further
  transcription change on these clean synthetic pages.
- **Preprocessing verified at the hook, honestly neutral on quality.** The
  POST rows record the real 205-03 chain doing exactly what it claims:
  `rotated-5deg` deskew estimates −5.0° and straightens the page, clean
  pages skip rotation (0°/−0.1° under the 0.3° gate), the long side is
  downscaled ≤1024, and payloads shrink on the small/dense pages
  (26981B → 19359B). On sparse synthetic pages the chain can re-encode
  larger than the input (the table/straight rows: 26182→28663B,
  50809→43347B mixed) — expected for mostly-white pages, logged by the
  module's payload-direction warn, and harmless (A2 held: the chat endpoint
  accepts the JPEG).
- **Classification honesty:** all 8 arm-runs classify `salvaged` — the
  done-less-stream quirk (260829-lkq) still fires on this engine
  revision AFTER the model has emitted complete, correct transcription
  (the content was already fully there — similarity 1.0 proves the
  accumulated markdown was the transcription). Per §4 these are degraded
  successes, not failures. `tokensUsed = 0` is part of the same quirk:
  the done-less close never delivers the final `done:true` chunk, so
  `eval_count` never arrives; duration/ttft remain real measurements.
- **num_ctx note for this run:** the suite runs the registry posture
  (`glm-ocr:latest` → `num_ctx 4096`, D-12 default). On this 0.9B model
  with ~15-word pages the prompt fits and the engine closes the stream
  done-less after the full transcription. The 205-01 baseline showed the
  OTHER 4096 failure mode (prompt+loop filling the window). Operators
  should still create `glm-ocr-optimized` (num_ctx 16384 — §2) for dense
  real-world pages; the runtime override is `OCR_NUM_CTX` (docs/CONFIGURATION.md).

### Render-scale decision (D-03, measured)

**PAGE_RENDER_SCALE stays a constant 3.0 (always-on)** — decided from the
205-03 unit measurements plus this suite's small-text arm, not conditionally:

- The suite's small-text POST row shows the preprocessing chain handling
  the half-point-size page with payload SHRINK (26981B → 19359B) and no
  quality regression (known-content 2/2, similarity 1.000 vs pre) — the
  ≤1024 downscale + q85 re-encode does not destroy the small glyphs the
  3.0-scale render preserves at the source.
- A conditional (precheck-gated) 3.0 would add a branching render path in
  4 call sites for a CPU delta this suite measures as bounded: even the
  worst fixture arm at 3.0-sourced rendering costs ~17s wall on a 16-thread
  CPU host — inside OCR_TIMEOUT's 10-minute budget by two orders of
  magnitude.
- The always-3.0 posture also keeps retries/repair consistent (the shared
  `PAGE_RENDER_SCALE` constant is imported by all four render call sites —
  one source of truth, no drift between first-pass and retry renders).
